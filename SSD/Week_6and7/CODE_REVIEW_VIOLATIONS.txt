VIOLATION #1: Excessive Chain Calls in ATM.java
--------------------------------------------------------------------------------
Location: ATM.java - Multiple locations in authenticate() and doChangePIN()

Issue:
Line 48: session.customer().getFullName()
Line 67: bank.getCustomerByCard(cardNumber)
Line 181: session.customer().getCard().getCardNumber()
Line 187: session.customer().getPrimaryAccountId()

Problem:
- Multiple method chains violate Law of Demeter
- ATM should not reach through Customer to get Card details
- Creates tight coupling between ATM -> Session -> Customer -> Card

Quick Solution:
Option 1: Add delegation methods to Session:
  public String getCustomerName() { return customer.getFullName(); }
  public String getCardNumber() { return customer.getCard().getCardNumber(); }

Option 2: Add methods to Customer:
  public String getCardNumber() { return card.getCardNumber(); }
  public boolean verifyPin(String pin) { return card.getPin().equals(pin); }

This reduces chains: session.getCustomerName() instead of session.customer().getFullName()

SOLID VIOLATION #1: Single Responsibility Principle (SRP)
--------------------------------------------------------------------------------
Location: ATM.java - The entire class

Issue:
ATM class has too many responsibilities:
1. User authentication
2. Menu management
3. Transaction orchestration
4. Account selection logic
5. Input validation
6. Receipt generation coordination
7. Business logic (PIN validation, amount checks)

Problem:
- Class is 202 lines doing multiple unrelated tasks
- Hard to test individual concerns
- Changes to authentication affect transaction handling

Quick Solution:
Split into multiple classes:

1. AuthenticationService.java:
   - Handle authenticate() logic
   - Manage PIN attempts
   - Card locking

2. TransactionCoordinator.java:
   - Execute transactions (doBalance, doWithdrawal, etc.)
   - Validate amounts
   - Log transactions

3. MenuController.java:
   - Handle mainMenu() logic
   - Menu display and navigation
   - User choice routing

4. AccountSelector.java:
   - Handle selectAccount() logic
   - Account display formatting

Each class would have ONE reason to change.


SOLID VIOLATION #2: Open/Closed Principle (OCP)
--------------------------------------------------------------------------------
Location: ATM.java, mainMenu() method, lines 87-109

Issue:
Switch statement with hardcoded transaction types:
  case 1 -> doBalance(session);
  case 2 -> doWithdrawal(session);
  case 3 -> doDeposit(session);
  ...

Problem:
- Adding new transaction type requires modifying ATM class
- Cannot extend without modification
- Violates OCP

Quick Solution:
Use Command Pattern or Strategy Pattern:

1. Create TransactionHandler interface:
   public interface TransactionHandler {
     void execute(Session session, ATM atm);
     String getMenuLabel();
   }

2. Implement for each transaction:
   public class BalanceInquiryHandler implements TransactionHandler {
     public void execute(Session session, ATM atm) { /* logic */ }
     public String getMenuLabel() { return "Balance inquiry"; }
   }

3. Register handlers in a map:
   Map<Integer, TransactionHandler> handlers = new HashMap<>();
   handlers.put(1, new BalanceInquiryHandler());
   handlers.put(2, new WithdrawalHandler());
   
4. Execute:
   TransactionHandler handler = handlers.get(choice);
   if (handler != null) handler.execute(session, this);

Now adding new transactions doesn't require changing ATM code.

SOLID VIOLATION #4: Interface Segregation Principle (ISP)
--------------------------------------------------------------------------------
Location: Bank.java

Issue:
Bank class exposes too many methods to all clients:
- Authentication methods (verifyPIN, lockCard)
- Account management (getBalance, withdraw, deposit, transfer)
- Customer management (addCustomer, getCustomerByCard)
- Transaction logging (logTransaction, getRecentTransactions)

Problem:
- Clients like ATM need all Bank methods
- Violates ISP: clients shouldn't depend on methods they don't use
- Different clients need different subsets of functionality

Quick Solution:
Split Bank into focused interfaces:

1. public interface AuthenticationService {
     boolean cardExists(String cardNumber);
     boolean verifyPIN(String cardNumber, String pin);
     void lockCard(String cardNumber);
   }

2. public interface AccountService {
     double getBalance(String accountId);
     void withdraw(String accountId, double amount);
     void deposit(String accountId, double amount);
     void transfer(String fromId, String toId, double amount);
   }

3. public interface CustomerService {
     Customer getCustomerByCard(String cardNumber);
     List<Account> getAccountsByCustomer(String customerId);
   }

4. public interface AuditService {
     void logTransaction(Transaction t);
     List<Transaction> getRecentTransactions(String customerId, int max);
   }

5. Bank implements all interfaces:
   public class Bank implements AuthenticationService, AccountService, 
                                CustomerService, AuditService { ... }

Clients depend only on interfaces they need.

SOLID VIOLATION #6: Open/Closed Principle (OCP)
--------------------------------------------------------------------------------
Location: Transaction.java hierarchy

Issue:
All transaction types have nearly identical structure:
- BalanceInquiry, Deposit, Withdrawal, Transfer, PinChange
- Each implements same methods with similar patterns
- Adding new transaction requires creating new class

Problem:
- Duplication across transaction classes
- toDisplayString() logic varies slightly but is repetitive

Quick Solution:
Use Template Method Pattern:

public abstract class Transaction {
  protected final String type;
  protected final LocalDateTime ts = LocalDateTime.now();
  protected final double amount;
  
  // Template method
  public String toDisplayString() {
    StringBuilder sb = new StringBuilder();
    sb.append(tsFmt()).append(" | ").append(type);
    appendDetails(sb);
    return sb.toString();
  }
  
  // Hook method for subclasses
  protected abstract void appendDetails(StringBuilder sb);
}

public class Deposit extends Transaction {
  protected void appendDetails(StringBuilder sb) {
    sb.append(" | acct=").append(accountId)
      .append(" | +").append(CurrencyUtil.fmt(amount));
  }
}

Reduces duplication and makes adding transactions easier.


SOLID VIOLATION #7: Open/Closed Principle (OCP)
--------------------------------------------------------------------------------
Location: CashDispenser.java

Issue:
Hardcoded denominations and fixed array size:
  private final int[] denom = {10, 20, 50, 100};
  private final int[] counts = new int[4];

Problem:
- Cannot add/remove denominations without modifying class
- Different ATMs might have different denominations
- Violates OCP

Quick Solution:
Make denominations configurable:

public class CashDispenser {
  private final List<Denomination> denominations;
  
  public static class Denomination {
    private final int value;
    private int count;
    
    public Denomination(int value, int count) {
      this.value = value;
      this.count = count;
    }
  }
  
  public CashDispenser(List<Denomination> denominations) {
    this.denominations = new ArrayList<>(denominations);
    this.denominations.sort((a, b) -> Integer.compare(b.value, a.value));
  }
  
  public CashDispenser(int... valueCountPairs) {
    this.denominations = new ArrayList<>();
    for (int i = 0; i < valueCountPairs.length; i += 2) {
      denominations.add(new Denomination(valueCountPairs[i], valueCountPairs[i+1]));
    }
  }
}

Now can create ATM with any denominations:
  new CashDispenser(5, 100, 10, 50, 20, 50, 50, 30, 100, 20)


SOLID VIOLATION #8: Single Responsibility Principle (SRP)
--------------------------------------------------------------------------------
Location: Keypad.java

Issue:
Keypad handles:
1. Integer input with validation
2. Double input with validation and formatting
3. String input
4. PIN input with console handling
5. Error messages to user

Problem:
- Mixing input reading with validation
- Mixing input with output (error messages)
- Too many different input types in one class

Quick Solution:
Split into InputReader and InputValidator:

1. InputReader.java:
   public class InputReader {
     private final Scanner scanner;
     
     public String readLine(String prompt) {
       System.out.print(prompt);
       return scanner.nextLine();
     }
     
     public String readSecure(String prompt) {
       Console console = System.console();
       if (console != null) {
         return new String(console.readPassword(prompt));
       }
       return readLine(prompt);
     }
   }

2. InputValidator.java:
   public class InputValidator {
     private final InputReader reader;
     
     public int readInt(String prompt) {
       while (true) {
         try {
           return Integer.parseInt(reader.readLine(prompt));
         } catch (NumberFormatException e) {
           System.out.println("Enter a valid integer.");
         }
       }
     }
   }

3. Keypad becomes a facade:
   public class Keypad {
     private final InputValidator validator;
     
     public int readInt(String prompt) {
       return validator.readInt(prompt);
     }
   }
